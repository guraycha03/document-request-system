SECTION 1: USER STORIES & ACCEPTANCE CRITERIA
----------------------------------------------

USER STORY 1 — REQUESTER
------------------------
As a requester, I want to submit a document request online so that I can formally 
request items or services without needing to visit the office physically.

Acceptance Criteria:
  AC1.1: A requester can submit a request with name, email, item, quantity (>0), 
         and purpose; the request is saved with status = 'pending'.
  AC1.2: Submitting quantity ≤ 0 is rejected with a validation error.

USER STORY 2 — STAFF REVIEWER
-----------------------------
As a staff reviewer, I want to view the list of pending document requests so that 
I can process, approve, or reject them in a timely manner.

Acceptance Criteria:
  AC2.1: Staff reviewer sees all requests filtered by status = 'pending' with 
         requester details and timestamps.
  AC2.2: Staff reviewer can change a request status to 'approved' or 'rejected'; 
         the change persists and updates updated_at.

USER STORY 3 — RECORD KEEPER
----------------------------
As a record keeper, I want all document request records stored with accurate 
creation and update timestamps so that I can maintain audit trails and historical 
reports.

Acceptance Criteria:
  AC3.1: Every request row has non-null created_at and updated_at timestamps.
  AC3.2: Record keeper can query all requests sorted by created_at descending to 
         generate audit reports.

SECTION 2: REQUEST TABLE DIAGRAM & DATA DICTIONARY
---------------------------------------------------

TABLE DIAGRAM (ERD-style)
-------------------------
+-------------------+-------------------------+------------------+
|      requests     |                         |                  |
+-------------------+-------------------------+------------------+
| PK  id            | BIGINT UNSIGNED         | Auto-increment   |
|     requester_name| VARCHAR(100)            | NOT NULL         |
|     requester_email| VARCHAR(255)           | NOT NULL         |
|     item_name     | VARCHAR(150)            | NOT NULL         |
|     quantity      | INT UNSIGNED            | NOT NULL, > 0    |
|     purpose       | TEXT                    | NOT NULL         |
|     status        | VARCHAR(20)             | DEFAULT 'pending'|
|     created_at    | TIMESTAMP               | NULLABLE         |
|     updated_at    | TIMESTAMP               | NULLABLE         |
+-------------------+-------------------------+------------------+

DATA DICTIONARY
---------------
| Field Name       | Data Type      | Constraints                    | Purpose                              |
|------------------|----------------|--------------------------------|--------------------------------------|
| id               | BIGINT UNSIGNED| PK, Auto-increment             | Unique identifier for each request   |
| requester_name   | VARCHAR(100)   | NOT NULL                       | Full name of the requester           |
| requester_email  | VARCHAR(255)   | NOT NULL                       | Contact email address of the requester|
| item_name        | VARCHAR(150)   | NOT NULL                       | Name of requested document/service   |
| quantity         | INT UNSIGNED   | NOT NULL, CHECK (quantity > 0) | Quantity of items requested (> 0)    |
| purpose          | TEXT           | NOT NULL                       | Detailed reason for the request      |
| status           | VARCHAR(20)    | DEFAULT 'pending'              | Current status of the request        |
| created_at       | TIMESTAMP      | NULLABLE, Auto                 | Record creation timestamp            |
| updated_at       | TIMESTAMP      | NULLABLE, Auto                 | Record last update timestamp         |

DESIGN EXPLANATIONS
-------------------
Quantity > 0:
  - An unsignedInteger permits zero, but a request for zero items is meaningless.
  - Application enforces quantity >= 1 via validation (DocumentRequestController::store()).
  - Sample entries all use positive quantities (1, 2, 1).

Default status = 'pending':
  - New requests begin as 'pending' so staff reviewers can triage them.
  - Migration sets DEFAULT 'pending'; omitting status on insert relies on this default.
  - Verified by sample row where status was omitted and became 'pending'.
